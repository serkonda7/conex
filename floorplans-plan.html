1. Scope

  • Sites and locations can have any number of image attachments (PNG / JPEG).
  • One attachment per site/location can be marked as the floor plan.
  • On a floor plan, users can define areas linked to other sites/locations and drag and drop devices and racks onto it.
  • Images are stored on disk; metadata lives in Postgres.
  • v2: cables drawn between placed markers. The placement coordinates are the endpoints, so v1 doesn't need to reserve anything else for them.
  • Out of v1: PDF/SVG upload, thumbnail generation, polygon editing UI (polygons are stored, the v1 editor draws rectangles), zoom/pan beyond fit-to-width.

2. Decisions

Question Decision
Area targets Any site or location the user can see, except the plan's own owner. Each target at most once per plan.
Upload limit 10 MB per image. No total quota.
Deleting a site/location Its attachments (and files) are deleted with it. If floor-plan data is affected, an explicit extra confirmation is required (see §6).
Storage On disk under the data dir. Postgres holds only metadata.
Ownership Attachments belong to exactly one site or one location.

3. Data model

Migration server/drizzle/0027_attachments_floorplans.sql (after the pending 0026_remove_tablet_role_icon). Tables are added to server/src/schema.ts. 

attachments
  id             integer identity PK
  site_id        integer FK sites      (nullable)
  location_id    integer FK locations  (nullable)   -- CHECK exactly one of site_id / location_id
  filename       text  not null        -- original name, for display / download
  mime           text  not null        -- 'image/png' | 'image/jpeg'
  size_bytes     integer not null
  width_px       integer not null
  height_px      integer not null
  storage_key    text  not null unique -- random uuid; file name on disk
  is_floorplan   integer not null default 0
  description    text
  created_at     bigint not null
  created_by     integer FK users on delete set null
  -- partial unique: (site_id)     WHERE is_floorplan = 1
  -- partial unique: (location_id) WHERE is_floorplan = 1
  -- index: site_id, location_id

floorplan_areas
  id             integer identity PK
  attachment_id  integer FK attachments not null
  site_id        integer FK sites      (nullable)   -- target
  location_id    integer FK locations  (nullable)   -- target; CHECK exactly one
  label          text                  -- null = target name
  points         jsonb not null        -- [[x, y], …] normalized 0..1, ≥ 3 points
  -- unique (attachment_id, site_id), unique (attachment_id, location_id)

floorplan_placements
  id             integer identity PK
  attachment_id  integer FK attachments not null
  rack_id        integer FK racks   unique (nullable)
  device_id      integer FK devices unique (nullable)  -- CHECK exactly one
  x, y           double precision not null             -- normalized 0..1

Rules

  • Positions belong to the image file. Coordinates are normalized, so replacing the file keeps areas and placements. Moving the floor-plan mark to another attachment discards the old plan's areas and placements, after a confirmation in the UI.
  • Areas and placements exist only on the marked attachment; the service rejects writes to an unmarked one.
  • Placement containment: a rack or device can be placed only on a plan whose owner contains it. That means its site, or its location or any ancestor of that location (via services/hierarchy.ts).
  • One plan per object: each rack or device appears on at most one plan (unique FK).
  • Tenant scope comes from the owning site or location; there is no own tenant_id.

4. File storage

  • Path: server/data/attachments/<storage_key>.png|jpg. It can be overridden in config.toml: 
    [storage]
attachmentsDir = "attachments"   # relative to the data dir, or absolute
    Resolved with resolveInDataDir; data/ is already gitignored.
  • Upload: stream to <key>.tmp, validate, then rename into place, then insert the DB row. If the insert fails, unlink the file.
  • Delete: delete the row(s) in the transaction and unlink the file(s) after commit.
  • Orphan sweep at startup (next to sweepExpired): remove files and stale .tmp files with no matching row. Log rows whose file is missing.
  • Validation: check the magic bytes (PNG signature, JPEG FF D8 FF), not the client Content-Type. Read the dimensions from PNG IHDR / JPEG SOF with a small helper in server/src/util/image.ts (no new dependency). Limit: 10 MB, enforced with Hono bodyLimit.
  • Serving: Bun.file() with ETag, Cache-Control: private, X-Content-Type-Options: nosniff and Content-Disposition: inline; filename="…", after an authz check on the owner's tenant.
  • Backup: the README backup section has to cover pg_dump and the attachments directory, kept in sync.

5. Server

Shared contracts (shared/src/schemas.ts)

  • AttachmentListQuerySchema with site / location filters.
  • AttachmentUpdateSchema: description, is_floorplan.
  • FloorplanPutSchema: { areas: [{ site_id | location_id, label?, points }], placements: [{ rack_id | device_id, x, y }] } with coordinates in 0..1.
  • Response types for attachment rows and the resolved plan (names, role icons, target links).
  • Add 'attachment' to CHANGE_OBJECT_TYPES.

Service (server/src/db/attachments.ts, returns Result)

  • listAttachments, getAttachment, createAttachment, replaceAttachmentFile, updateAttachment, deleteAttachment.
  • Floor-plan mark: setting is_floorplan unsets the previous mark and clears that plan's areas and placements in the same transaction.
  • getPlan filters out areas and placements whose objects are outside the user's tenant scope.
  • putPlan replaces areas and placements atomically. It validates targets (visible, not the owner, no duplicates) and containment, and writes one changelog entry per save. Items hidden from a tenant-scoped user are kept unchanged on save.
  • Changelog entries on upload, update, replace, delete and plan save (object_type = 'attachment').

Routes (server/src/routes/attachments.ts, mounted at /attachments)

Wired by hand, not through makeTenantApp, because they include multipart and binary endpoints. Permissions are the existing view / edit / delete.

Method Path Purpose
GET /attachments?site=|location= List attachments of an owner
POST /attachments Multipart upload: file, site_id | location_id, description
PATCH /attachments/:id Description, floor-plan mark
PUT /attachments/:id/file Replace the image, keeping the plan
DELETE /attachments/:id Delete the attachment (confirm flow, §6)
GET /attachments/:id/file Serve the image
GET /attachments/:id/plan Areas and placements, resolved
PUT /attachments/:id/plan Save areas and placements atomically

Effects on existing services

  • db/racks.ts, db/devices.ts: when a rack or device moves out of the plan owner's scope (site, location or rack change), delete its placement in the same transaction. Deleting a rack or device deletes its placement.
  • db/tenancy.ts: when a location's parent_id changes, drop placements that are no longer contained. Site and location deletes cascade as described in §6.

6. Delete behaviour

Deleting a site or location deletes its attachments, their files, its own plan's areas and placements, and every area on other plans that targets it.

Extra confirmation is required when floor-plan data is affected, i.e. the object has a marked floor plan with areas or placements, or it is the target of an area on another plan.

  • Server: DELETE /sites/:id and /locations/:id (and DELETE /attachments/:id for a marked plan) answer 409 with an impact summary when floor-plan data is affected and ?confirm=floorplan is missing: 
    { "error": "…", "floorplan": { "areas": 3, "placements": 12, "linkedFrom": 2 } }
    With the flag, they delete as described above. Other delete blocks (child locations, racks, …) still apply first.
  • Client: useDetailDelete (components/detail_page.tsx) keeps its normal confirm. On that 409 it shows a second confirm that lists the impact, then retries with the flag. The attachment delete in the gallery uses the same flow.
  • Plain attachments that aren't marked as the floor plan are deleted after the normal single confirm.

7. Client

API

client/src/api/attachments.ts: list, upload (FormData), update, replace, delete, getPlan, putPlan, plus a file URL helper.

AttachmentsSection (site and location detail pages)

  • Thumbnail grid (CSS-scaled originals).
  • Upload through a button or by dropping files onto the grid. Type and size are checked client-side before upload.
  • Click opens a lightbox (components/modal.tsx).
  • Per image: edit the description, mark as floor plan (star icon; asks for confirmation when this replaces an existing plan that has content), replace the file, delete.

FloorplanSection (shown when a floor plan is marked; anchor #floorplan)

  • View mode: the image at fit-to-width, with an SVG overlay (viewBox="0 0 1 1", preserveAspectRatio="none") for area polygons with labels. Markers are absolutely positioned elements using percentage coordinates: rack icon for racks, device role icon (lib/icons.ts) for devices.
    • Clicking an area opens its target at #floorplan, so you can drill down site → floor → room.
    • Clicking a marker opens the rack or device. Hovering shows a tooltip with name and status.
  • Edit mode (only with the edit permission):
    • Area tool: drag to draw a rectangle, then pick the target site or location with components/object_selector.tsx. Areas can be moved, resized, relabelled and deleted.
    • Palette: a side list of unplaced racks and devices from the owner's scope, grouped and searchable. Drag items onto the plan with HTML5 drag-and-drop. Existing markers are moved with pointer events and removed with ×.
    • Save / Cancel: Save calls PUT /plan once. Leaving with unsaved changes asks for confirmation.

Other pages

  • The rack and device detail pages show an "On floor plan of X" link.
  • The site and location detail pages show "Linked from Y" when an area on another plan targets them.

i18n

New keys attachment.* and floorplan.* in client/src/i18n/en.ts and de.ts. No hardcoded strings.
