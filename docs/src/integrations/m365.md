# Microsoft 365
Liest die Entra-Mandanten der Kunden: jeder conex-Mandant wird mit genau einem
Entra-Mandanten verknüpft, dessen Benutzer werden mit den Mitarbeitern abgeglichen.
Die Funde erscheinen im [Datenabgleich](consistency.md) wie bei TANSS.

conex schreibt nie nach Microsoft 365.

**Voraussetzung:**
- eine Entra-App im eigenen Mandanten des Dienstleisters
- `frontendUrl` in der `config.toml` (öffentliche Adresse von conex), sonst wird die
  Adresse des Browsers verwendet, der den Zustimmungslink erstellt


## Verhalten
- Pro Kunden-Mandant werden Name und verifizierte Domains (`/organization`) sowie die
  Mitglieder (`userType eq 'Member'`, keine Gäste) gelesen.
- **Nur lizenzierte Benutzer** (Standard): Konten ohne Lizenz (freigegebene Postfächer,
  Raumpostfächer, Dienstkonten) werden ignoriert.
- Zuordnung zu Mitarbeitern: erst über die Mail-Adresse (`mail`, sonst UPN), dann über
  den Namen.
- **Extern inaktiv, in conex noch aktiv**: das Konto ist in Entra deaktiviert, der
  Mitarbeiter in conex aber aktiv. Das ist das Signal für ein Offboarding; die Aktion
  **In conex inaktiv setzen** behebt es.
- **Mail-Domain im Entra-Mandant nicht verifiziert**: die Domain der ersten
  Mail-Adresse des conex-Mandanten fehlt unter den verifizierten Domains.
- Fehlende Mitarbeiter lassen sich mit **In conex importieren** anlegen.
- Geräte (Intune) werden noch nicht abgeglichen.
- Schlägt ein Mandant fehl (z. B. Zustimmung entzogen), bleibt sein letzter Stand
  erhalten und der Fehler steht in der Liste der Mandanten. Die anderen Mandanten
  laufen weiter.


## 1. Entra-App registrieren
Im eigenen Mandanten des Dienstleisters:

1. [Entra Admin Center](https://entra.microsoft.com) → **Anwendungen →
   App-Registrierungen → Neue Registrierung**: Name `conex`,
   **Konten in einem beliebigen Organisationsverzeichnis (mehrinstanzenfähig)**.
2. **Umleitungs-URI**: Plattform **Web**, `https://<conex>/api/integrations/m365/consent`
   (genau die `frontendUrl` mit diesem Pfad).
3. **Anwendungs-ID (Client-ID)** und **Verzeichnis-ID (Mandanten-ID)** notieren.
4. **Zertifikate & Geheimnisse → Neuer geheimer Clientschlüssel**: den *Wert* sofort
   kopieren und das Ablaufdatum notieren (höchstens 24 Monate). Danach stoppt der
   Abgleich für **alle** Kunden.
5. **API-Berechtigungen → Berechtigung hinzufügen → Microsoft Graph →
   Anwendungsberechtigungen**:
   - `Organization.Read.All`
   - `User.Read.All`

   Die Standardberechtigung `User.Read` (delegiert) kann bleiben.
   Im eigenen Mandanten ist keine Administratorzustimmung nötig.


## 2. conex einrichten
**Integrationen → Microsoft 365 → Einrichten** (Berechtigung `integrations.manage`):

1. **Anwendungs-ID (Client-ID)**, **Heimat-Mandant** (Verzeichnis-ID oder Domain aus
   Schritt 1) und **Geheimer Clientschlüssel** eintragen.
2. **Schlüssel läuft ab**: optional; conex warnt 30 Tage vorher auf der
   Integrationsseite.
3. **Verbindung testen** muss erfolgreich sein, dann **Speichern**.


## 3. Kunden verbinden
Auf der Seite des conex-Mandanten, Karte **Microsoft 365** (nur globale Benutzer mit
`integrations.manage`):

1. **Zustimmungslink erstellen**, dann **Zustimmungslink öffnen** oder **Link
   kopieren** und an den globalen Administrator des Kunden senden. Der Link ist
   14 Tage gültig.
2. Der Administrator meldet sich an und erteilt die Zustimmung für die Organisation.
   Er landet auf einer Bestätigungsseite von conex (ohne conex-Anmeldung).
3. conex prüft die Zustimmung selbst (Token für den Mandanten, `/organization` lesen),
   verknüpft den Mandanten und startet einen Abgleich.

Wurde die Zustimmung schon anders erteilt (z. B. über das Entra Admin Center des
Kunden), unter **Zustimmung schon erteilt** die Mandanten-ID oder eine Domain
eintragen und **Prüfen und verbinden** klicken.

**Trennen** entfernt nur die Verknüpfung. Unter **Integrationen → Microsoft 365**
entfernt **Entfernen** einen Kunden-Mandanten ganz aus conex. Die Zustimmung selbst
widerruft der Kunde in seinem Entra unter **Unternehmensanwendungen → conex →
Löschen**.


## Fehlerbehebung
| Fehler                                     | Ursache                                                                                          |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| `AADSTS7000215: Invalid client secret`     | Geheimnis falsch kopiert oder abgelaufen: neues anlegen, in conex eintragen.                     |
| `AADSTS700016: Application … was not found` | Im Kunden-Mandanten wurde (noch) nicht zugestimmt, oder falsche Client-ID / falscher Mandant.  |
| `AADSTS50011: … redirect URI … does not match` | Umleitungs-URI in der App fehlt oder weicht ab (`frontendUrl`, Pfad, `https`).               |
| `AADSTS65004: User declined to consent`    | Der Administrator hat abgelehnt.                                                                 |
| `Authorization_RequestDenied` / 403        | `Organization.Read.All` oder `User.Read.All` fehlt, oder die Zustimmung erfolgte vor dem Hinzufügen: neu zustimmen lassen. |
| `Invalid consent link` / abgelaufen        | Link verändert oder älter als 14 Tage: neuen Link erstellen.                                     |

Direkt nach der Zustimmung kann Entra noch einige Sekunden Token ablehnen; conex
versucht es dreimal. Schlägt es trotzdem fehl, später **Prüfen und verbinden** nutzen.
