Plan: Virtual machines on top of devices

conex · drafted 2026-10-16

Decisions

Topic Decision
Data model A separate virtual_machines table, not a host reference on devices
Tenant A hosted VM always has its host's tenant. Only a hostless VM sets its own tenant
Host Optional. Hostless means a cloud / IaaS VM
Fields No OS field, and no hardware data (vCPU / memory / disk) for now
UI No separate list page. VMs are listed in the devices table
VM pages Separate detail and add/edit pages under /devices/vm/…
Names Unique per host. Hostless VMs: unique per tenant (or among hostless VMs without a tenant)

1. Schema

server/src/schema.ts, migration server/drizzle/0031_virtual_machines.sql (generated with drizzle-kit). 

// ---------------------------------------------------------------------------
// Virtual machines. A VM runs on a host device, or has no host (IaaS / cloud).
// A hosted VM always carries its host's tenant: the service layer copies it on
// create and on host change, and a host tenant change re-tenants its VMs in the
// same transaction. Only a hostless VM sets its tenant freely. A device can't
// be deleted while VMs run on it, so the host FK carries no cascade.
// ---------------------------------------------------------------------------

export const virtual_machines = pgTable(
	'virtual_machines',
	{
		id: integer('id').primaryKey().generatedByDefaultAsIdentity(),
		// Null = hostless (cloud / IaaS).
		host_device_id: integer('host_device_id').references(() => devices.id),
		device_role_id: integer('device_role_id')
			.notNull()
			.references(() => device_roles.id),
		status: text('status').notNull().default('active'),
		name: text('name').notNull(),
		tenant_id: integer('tenant_id').references(() => tenants.id),
		employee_id: integer('employee_id'),
		description: text('description'),
	},
	(table) => [
		index('virtual_machines_host_device_id_idx').on(table.host_device_id),
		index('virtual_machines_device_role_id_idx').on(table.device_role_id),
		index('virtual_machines_tenant_id_idx').on(table.tenant_id),
		index('virtual_machines_employee_id_idx').on(table.employee_id),
		index('virtual_machines_status_idx').on(table.status),
		index('virtual_machines_name_idx').on(table.name),
		uniqueIndex('virtual_machines_host_name_idx').on(table.host_device_id, table.name),
		// Hostless VMs: name unique per tenant. Two partial indexes because
		// NULL tenants never collide in a plain unique index.
		uniqueIndex('virtual_machines_hostless_tenant_name_idx')
			.on(table.tenant_id, table.name)
			.where(sql`${table.host_device_id} IS NULL AND ${table.tenant_id} IS NOT NULL`),
		uniqueIndex('virtual_machines_hostless_untenanted_name_idx')
			.on(table.name)
			.where(sql`${table.host_device_id} IS NULL AND ${table.tenant_id} IS NULL`),
		foreignKey({
			name: 'virtual_machines_employee_tenant_fk',
			columns: [table.employee_id, table.tenant_id],
			foreignColumns: [employees.id, employees.tenant_id],
		}),
		check(
			'virtual_machines_employee_requires_tenant',
			sql`${table.employee_id} IS NULL OR ${table.tenant_id} IS NOT NULL`,
		),
	],
)

Keeping the tenant in sync (service layer)

Tenants are nullable, so a composite FK to devices(id, tenant_id) can't enforce the rule: Postgres skips the check whenever a column is NULL. tenant_id stays a real column so that list scoping, checkTenant and the employee FK work the same as for devices. The service keeps it in sync:

  • When a VM is created or its host_device_id changes, tenant_id is set to the host's tenant. A tenant_id sent by the client for a hosted VM is rejected.
  • When a host's tenant changes in updateDevice (including the move-tenant dialog), all of its VMs get the new tenant_id in the same transaction. A VM's employee_id is cleared, because the old employee no longer belongs to the tenant.
  • When a VM is detached from its host, it keeps its current tenant, which can be edited from then on.

2. Shared contracts

shared/src/schemas.ts

  • VirtualMachineCreateSchema / VirtualMachineUpdateSchema (strict objects), plus their inferred types. Status reuses DeviceStatusSchema.
  • DeviceListQuerySchema gets a new kind filter (device / vm) and a host filter.
  • The list row type gets a discriminator: { kind: 'device', … } | { kind: 'vm', … }.
  • Add 'virtual_machine' to CHANGE_OBJECT_TYPES (changelog and audit log).

3. Server

  • server/src/db/virtual_machines.ts: get, create, update and delete, all returning Result. Guards: host exists, tenant rule (above), checkEmployeeAssignment, role exists. A duplicate name (same host, or same tenant for hostless VMs) returns a ConflictError. This is checked up front and also mapped from the unique-index violation, like duplicateDeviceError. Writes go through logCreate / logUpdate / logDelete.
  • server/src/db/devices.ts:
    • listDevices becomes a UNION ALL of devices and VMs, with the same sort and paging and a count across both.
    • The rack, device_type, site and placed filters only apply to devices, so setting one hides VMs.
    • deleteDevice returns a ConflictError while VMs run on the device.
    • updateDevice re-tenants the device's VMs when its tenant changes.
  • server/src/db/device_roles.ts: the role delete guard also counts VMs.
  • server/src/db/owners.ts: add virtualMachineTenant(id).
  • server/src/routes/virtual_machines.ts: CRUD under /api/virtual-machines, with the same middleware and authz as devicesApp (checkTenant, resolveCreateTenant, checkUpdateTenant). Listing goes through GET /api/devices.
  • server/src/db/search.ts: VM names show up in the device group, or a group of their own.

Other UI

  • VM pages: small detail and add/edit pages under /devices/vm/…, built on detail_page / form. The host is picked with device_search.tsx; empty means hostless. The tenant field only shows for hostless VMs.
  • Device detail: a "Virtual machines" card for the host, with an "Add VM" button that fills in the host.
  • API client: client/src/api/virtual_machines.ts; api/devices.ts picks up the union row type.
  • Routes: app/routes.ts and breadcrumbs.
  • i18n: vm.* keys in en.ts and de.ts.
